# PRD 模板与交付标准

## 一、先定档位

| 档位 | 篇幅 | 回答什么 | 用于 |
|------|------|---------|------|
| speclet | 一段话 + 2-3 个开放问题 | 问题是否成立、值得继续探 | 探索期、立项前 |
| 1 页 PRD（默认） | 1-2 页 | 为谁解决什么、不做哪些、怎么算成功 | 团队评审、跨职能对齐 |
| 完整 PRD | 全模板展开 | 边界条件、验收、埋点、依赖是否齐 | 开发交接、上线准备 |

判定：用户说「给开发排期 / 上线 / 交接」→ 完整档；说「先对齐 / 评审 / 看看值不值得做」→ 1 页或 speclet；没说默认 1 页，并在文首标注档位。超过 2 页仍未做完决策，先砍内容而不是继续写。

## 二、1 页版骨架（默认档，硬上限）

标注「1 页」时**只能**用下面这个骨架，不得套用完整模板的 8 章。

```markdown
# [产品名] · 1 页 PRD
> 档位：1 页　状态：草稿　日期：[YYYY-MM-DD]

## 问题与用户
[谁、在什么场景、多久发生一次、现在的笨办法、造成什么损失；证据一句带出处]

## 目标与成功标准
| 类型 | 指标 | 基线 | 目标 | 时限 | 来源 |

## 方案范围
[做哪几件事；依赖顺序]

## 明确不做
- [排除项 + 为什么 + 何时再看]

## 待验证与下一步
[已定决策 / 待验证假设 / 下一步]
```

**硬上限：≤5 个内容段（含结尾）+ ≤2 张表。** 判定「还是不是 1 页」用可数规则：

- 出现 **≥5 个数字编号章标题**（`## 1.` … `## 5.`）⇒ 已经不是 1 页，要么改标为完整档，要么砍回骨架。
- 出现「非功能需求 / 数据埋点 / 风险与依赖 / 附录」等完整档专章 ⇒ 同上。
- speclet 只写「问题 + 2-3 个开放问题」一段，不给表格。

档位名与篇幅必须自洽：标 1 页却展开成 7 章，按「档位标注失真」处理——这不是风格问题，是让评审方无法判断该读到什么粒度。

## 三、完整模板

```markdown
# [产品名称] 产品需求文档 v0.1

> 档位：完整 / 1 页 / speclet　状态：草稿　日期：[YYYY-MM-DD]

## 1. 概述
### 1.1 背景
[为什么现在做：市场变化 + 用户需求 + 业务目标，不写功能介绍]
### 1.2 一句话定位
[产品名称] 是一个面向 [目标用户] 的 [产品类型]，解决 [核心问题]。
### 1.3 目标用户
[岗位 / 规模 / 技术程度 / 使用场景 / 痛点 / 动机；买方与使用者分开写]
### 1.4 成功标准
| 类型 | 指标 | 当前基线 | 目标值 | 时限 | 数据来源 |
|------|------|---------|--------|------|---------|
| 主指标 | [唯一一个判断成败的指标] | [数值/无] | [数值] | [日期] | [埋点/后台] |
| 次级 | [2-3 个] | | | | |
| 护栏 | [不能被牺牲的] | | | | |
| 反指标 | [涨了反而说明有问题] | | | | |
### 1.5 竞品与替代方案

- [竞品官网 / 行业报告 / 访谈记录路径]

## 2. 用户与场景

### 2.2 用户旅程

## 3. 功能需求

|------|------|--------|------|

[前置条件 / 主流程 / 分支 / 异常 / 空状态 / 权限]
### 3.3 明确不做
- [本期不做的事 + 为什么不做 + 什么时候可能做]
### 3.4 验收标准

|------|----------------|---------|

| 类型 | 要求 |

| 事件名称 | 触发时机 | 参数 | 对应指标 |
|---------|---------|------|---------|

| 风险/依赖 | 影响 | 应对措施 | 负责人 |

### 7.1 待验证假设
| 假设 | 验证方式 | 需要的数据 | 谁去验 |
|------|---------|-----------|--------|
### 7.2 开放问题
| 问题 | 影响范围 | 需要谁拍板 | 截止时间 |
|------|---------|-----------|---------|

## 8. 附录
- 修订记录 / 术语表 / 决策日志（每次范围变更记一条：时间、改了什么、为什么）
```

### 「明确不做」写法

这是最容易缺、也最省返工的一节。必须有真实排除项，不能写「其他暂不考虑」。

- 差：`暂不做高级功能`
- 好：`本期不做多语言（目标市场仅国内，V2 再评估）；不做导出 Excel（有 API 的客户 <5%，先看日志需求）`

## 四、指标写法

四件套缺一不可：主指标（判断成败的唯一数字）、次级（2-3 个解释原因）、护栏（不能被牺牲的）、反指标（涨了反而说明有问题）。

| 类型 | 差 | 好 |
|------|----|----|
| 主指标 | 「提升用户活跃」 | 「7 日功能激活率，定义：首次触达后 7 天内完成 ≥1 次核心动作的用户占比；基线 无（新功能）；目标 30%，上线后 90 天评估；来源 埋点 feature_action_completed」 |
| 次级 | 「关注用户满意度」 | 「功能完成率与帮助中心该功能页访问量，用于解释主指标波动的原因」 |
| 护栏 | 「保证性能」 | 「核心页 P95 从 1.4s 不劣于 2.0s，超过则暂停放量」 |
| 反指标 | 无 | 「重复操作次数上升可能是流程难用（伴随完成率下降即为摩擦），需与任务完成率交叉看」 |

规则：指标必须有定义、来源、基线、目标、时限；缺埋点标 `[需埋点]`；指标超过 5 个通常说明没想清主次。复合指标（加权分、健康分之类）要写清权重与观察窗口。

## 五、红队评审（交稿前自跑一遍）

按角色各问 2 个最可能被问倒的问题，只保留**会改变范围、方案或指标**的意见。

| 角色 | 典型问题 |
|------|---------|
| 工程 | 哪个技术假设最可能不成立？边界条件（空、超大、并发、离线）写了吗？ |
| 设计 | 主流程有几步是多余的？空状态、失败状态、首次使用长什么样？ |
| 数据 | 这个指标能测出来吗？埋点谁来加？成功/失败如何归因？ |
| 安全合规 | 有哪些个人数据？越权、导出、删除怎么做？ |
| 财务/商务 | 单价与成本撑得住吗？这个投入的机会成本是什么？ |
| 客服/销售 | 用户会怎么问？上线后一周最可能收到什么投诉？ |
| 竞对 | 对手下个版本就能做掉吗？我们的差异点守得住吗？ |

收敛规则：输出三栏——**必改**（不改就别发）、**待确认**（需要某人拍板）、**记录**（可延后）。不把红队意见直接堆进 PRD 正文。

## 六、交付前自检清单

- [ ] 档位明确，篇幅与档位匹配
- [ ] 问题有证据（访谈原话 / 工单量 / 数据 / 竞品事实），推断已标 `[假设]`
- [ ] 目标用户是具体角色，不是「用户」
- [ ] 「明确不做」有真实排除项与原因
- [ ] 每个 P0 功能有可测验收标准（含异常与空状态）
- [ ] 指标四件套齐全，各带基线、目标、时限、来源
- [ ] 非功能需求写了性能、安全、兼容性、可靠性
- [ ] 埋点与指标一一对应，缺的标 `[需埋点]`
- [ ] 风险有应对措施与负责人
- [ ] 开放问题有拍板人和截止时间
- [ ] 各章节数字、范围、优先级互相自洽
- [ ] 无遗留占位符：占位要么填上，要么标 `[待确认]` / `[需埋点]`
- [ ] 结尾给出：已定决策 / 待验证假设 / 下一步
