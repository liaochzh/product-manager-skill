# 需求质量审计（18 条特征）

用于评审已有 PRD / 用户故事 / 验收标准，也用于写作时自检。顺序不能反：**先判抽象层级，再逐条审**。

## 一、先判抽象层级

| 层级 | 在说什么 | 例子 | 谁拥有 |
|------|---------|------|--------|
| 业务 / 战略 | 为什么要做、要什么业务结果 | 12 个月内把偏好类投诉降低 40% | 业务负责人 |
| 干系人 / 用户 | 某类用户需要系统提供什么能力 | 客户可在任意入口更新偏好，且全渠道生效 | 用户代表 |
| 方案 / 功能 | 系统具体怎么表现 | 偏好服务在写入后 5 秒内（P95）同步到所有渠道 | 交付团队 |

高层级需求**不是**低层级需求的缺陷版。要求战略级需求写出接口延迟，属于过早拆解，会把设计假设钉死。

三个陷阱：
- 用方案级标准审用户级需求 ⇒ 误报「不够具体」。
- 用业务级标准审方案级需求 ⇒ 漏掉边界与异常。
- 层级混在一句里 ⇒ 先拆成两句再评。

判定线索：句子里出现「任一入口 / 全渠道 / 所有客户」多半是用户级；出现具体组件、延迟、错误码、字段，一定是方案级。层级不明时先问用户要哪一层，不要默认往方案级压。

## 二、18 条特征

单条特征（逐条需求看）：1-9；集合特征（整套需求看）：10-18。

| # | 特征 | 检验方法 | 常见坏味道 |
|---|------|---------|-----------|
| 1 | 无歧义 | 两个合格读者独立读，会不会得出不同理解（进而实现不一致） | 「合理时间内响应」 |
| 2 | 清晰易懂 | 目标读者一遍能懂，不需要内部黑话 | 自造缩写、堆术语 |
| 3 | 内聚 | 一条需求只表达一个用户意图 | 把注册、邀请、权限塞进一条 |
| 4 | 一致 | 与其他需求、术语表不冲突 | 同一概念三种叫法 |
| 5 | 符合规范 | 遵守公司/法规/平台约束 | 违反平台审核或隐私要求 |
| 6 | 时效 | 仍然对应当前产品与市场 | 引用已下线功能 |
| 7 | 可修改 | 改一处不需重写全文，不牵连无关章节 | 全局散落硬编码数字 |
| 8 | 可追溯 | 能追到来源（访谈、工单、目标）与下游（功能、验收） | 需求凭空出现，无出处 |
| 9 | 相关 | 服务于当前目标，不是「顺手也做了」 | 夹带私人偏好的功能 |
| 10 | 唯一 | 整套文档里没有重复表述 | 功能表与详细说明重复且不一致 |
| 11 | 分类 | 按模块/类型归位，能检索 | 全部塞进「其他」 |
| 12 | 完整 | 主路径 + 关键分支 + 关键失败态 + 谁受影响 | 只写 happy path |
| 13 | 正确 | 事实、数字、引用准确 | 基线数字过期、引用错版本 |
| 14 | 简明 | 一句话能说清的不写一段 | AI 式铺陈、同义反复 |
| 15 | 可测 | 能写出具体输入与预期输出 | 「体验流畅」「尽量快」 |
| 16 | 实现无关 | 在规定层级上不预设技术方案 | PRD 里写「用 Redis 缓存」 |
| 17 | 有主 | 每条有负责人，能回答「谁定的」 | 无人认领的待办需求 |
| 18 | 可行 | 在给定人、时间、预算、合规下做得到 | 两周做完整推荐系统 |

层级改写：高层级需求在 12/15/16 上按本层标准判，不算缺陷。「待设计阶段决定」的细节单列成**拆解时待决清单**，不塞进缺陷日志。

## 三、模糊词表（出现即标，不自动判错）

适当、合理、友好、易用、直观、高效、快速、稳定、安全、现代、简洁、易上手、无缝、灵活、优化、高质量、足够、正常、典型、标准、按需、视情况、必要时、尽可能、等等、和/或、可以、可能。

处理：能给出数值/条件就量化，给不出就写成待验证假设或开放问题。

- 差：报告对经理和相关人员可用。
- 好：角色为 {经理, 区域总监, 审计} 可打开销售报表；其他角色拒绝访问。

## 四、可测化改写

| 原文 | 改写 |
|------|------|
| 搜索要快 | 1000 并发下，搜索结果页 P95 ≤ 2s |
| 支持大文件上传 | 单文件 ≤ 2GB；断点续传；失败自动重试 3 次后提示 |
| 界面要好看、有高级感 | 首屏 3 秒内可交互；主操作在首屏可见；空状态有引导文案与主按钮 |

## 五、落地方式

- **PRD 验收标准**：用「给定—当—则」写；一条验收只验一件事；必须覆盖异常与空状态。
- **用户故事**：`作为[具体角色]，我要[能力]，以便[可验证的价值]`；价值写不出可验证结果，说明故事没想清。
- **审计输出格式**：缺陷日志（编号 / 原文 / 违反特征 / 建议改写）+ 拆解时待决清单 + 一句总体结论（可用 / 需修改后可用 / 需重写）。不要为凑条数把高层级需求判成缺陷。
